# H1 harness probe: cost and speed of the CPU double (PLAN_TWIN section 3 H1, section 6)

Lane S5a-H1, Sat 17 Oct 2026 ~21:54-22:20 (local). Code at branch `lane/S5a-H1`.

## What was run

- Code path: `ros2/intercycle_eval/intercycle_eval/batch.py --backend fake` on the body-shop `fake_episode`
  (bridge + Nav2 + kinematic test double + plant + broadcaster), one Modal container per episode.
- New in the code: `cloud/modal_isaac_robot.py::fake_episode_cpu(cpu)` returns `fake_episode.with_options(cpu=cpu)`
  (memory stays 8192 MiB; 0 = the decorator's cpu=8). `batch.py` got `--cpu` and `--max-rtf` (sealed default stays 1.0).
  `IC_MODAL_APP` env var overrides the Modal app name (used: `S5a-H1-probe`).
- Mission: 720 s of sim time (`--seconds 720`), condition `learned` (the heaviest: it adds the broadcaster and
  LearnedObserver), seeds 20 and 21, 2 runs per setting, 4 settings, each setting in its own Modal app.
- Map: `out/r3/maps/dev_layered_map.npz` was NOT present anywhere (out/ is gitignored and the old map is gone). I built a
  stand-in with `scripts/build_map.py --quick --workers 6 --trials 10` (17 s, heavy lock taken and released). It is a
  small map from three short windows, not the 1-week map. The fake backend needs only a LayeredMap npz in the world
  bytes, so the wall time and cost do not depend on its quality; the mission outcomes (inspections 0-2 of 10) do and are
  not a result.
- Plus 1 extra batch at cpu=4, rtf 2 with conditions `none` and `static` (seed 20) to see whether other conditions cost
  the same.

## Rates used

Modal Functions, standard container, from modal.com/pricing (fetched 17 Oct 2026):
CPU $0.0000131 per core-second, memory $0.00000222 per GiB-second, billed at the greater of reserved and used, minimum
0.125 core. With memory 8 GiB:

| cpu | $/container-second | $/container-hour |
|---|---|---|
| 8 | 0.00012256 | 0.441 |
| 4 | 0.00007016 | 0.253 |

Check against Modal's own billing report (`modal.billing.workspace_billing_report`, hourly): only the 20:00-21:00 UTC
bucket is published so far, and my apps straddle 21:00 UTC. For the part inside that bucket, reserved-resource seconds x
rate predicts $0.0784 / 0.0321 / 0.0321 / 0.0561 and Modal billed $0.0770 / 0.0312 / 0.0310 / 0.0590 (cpu8 rtf2, cpu4
rtf2, cpu4 rtf1, cpu8 rtf1). Within 5 %, so the reservation formula is the real bill. The sim is wall-paced (physics alone
runs 130-150x real time), so the reserved cores sit mostly idle and the bill is wall seconds x reservation. The full
per-app billed totals will appear in the hourly report after 22:00 UTC; the totals below are computed, not read from it.

## Results (condition learned, 720 s sim, 2 runs per setting)

| cpu | max_rtf | wall per mission (in container) | batch wall incl. start-up | first-frame boot | $/run (run only) | $/run (container lifetime) |
|---|---|---|---|---|---|---|
| 8 | 1 | 724.9, 769.1 s = 12.1, 12.8 min | 817.7 s | 4.0, 43.1 s | 0.0916 | 0.1002 |
| 4 | 1 | 723.9, 725.9 s = 12.1 min | 747.1 s | 3.0, 4.0 s | 0.0509 | 0.0524 |
| 8 | 2 | 367.0, 366.0 s = 6.1 min | 397.0 s | 6.0, 5.0 s | 0.0449 | 0.0487 |
| 4 | 2 | 367.0, 368.0 s = 6.1 min | 394.2 s | 5.0, 7.0 s | **0.0258** | **0.0277** |

- "Run only" = mean in-container `total_wall_s` x rate. "Container lifetime" = batch wall (start-up, world upload, run,
  result return, until the app stops) x rate; it is what an isolated 2-container batch is billed. Warm containers reused
  across many episodes would sit between the two.
- Boot time: `phases.boot_wall_s` (container Python start to first bridge frame) is 3-7 s, one outlier of 43 s on a slow
  host (cpu8 rtf1 seed 21: physics-only rtf 38 instead of 130-150, sensors 76 s instead of 13-19 s). Cold start of the
  container itself (schedule, image from cache, world upload, result return) is batch wall minus slowest in-container run:
  16-30 s typical (21, 26, 30, 16 s), 49 s for the slow host.
- rtf 2 is reachable on both sizes: achieved rtf 2.0, wall 360 s of sim loop. cpu=4 gives the same wall as cpu=8
  (the process is pacing-bound, not CPU-bound), so cpu=4 is strictly cheaper.
- Early finish changes cost: `static` seed 20 finished its round at 271.7 s wall (SUCCEEDED, 10/10) and `none` ran the full
  366 s (INTERRUPTED, 5/10, 4 trips). So the 720 s figure is the upper bound per run; a condition that completes early is
  cheaper. Whether the twin's double ends early after its round is the lead's / S5a's call; I priced the full 720 s.
- Not measured, not recommended without a test: max_rtf above 2. Physics-only headroom is large, but Nav2 and the
  bridge exchange (60 s of the profile) were not stressed past 2x, and rtf 2 vs the Isaac mission rate matters for G2
  parity ("same max_rtf as the sealed double").
- Mission outcomes (path 12-84 m, inspections 0-2/10 on the learned runs) are wiring-check output on a stand-in map and
  are not used for anything here. One run (cpu8 rtf1 seed 20) walked only 12 m.

## Applying the plan's rule (RECOMMENDATION only)

Runs: tuning 64 (2 arms x 8 configs x 4 worlds) + dev 40 (<= 20 per arm) + sealed 320 (5 x 16 x 2 x 2) = 424.
Plan assumption: $0.04/run -> $16.96. Threshold in the plan: tuning + dev + sealed <= $10.6.

Total for 424 runs (run only / container lifetime):

| cpu / rtf | $/run | 424 runs |
|---|---|---|
| 8 / 1 | 0.092-0.100 | 38.8 - 42.5 |
| 4 / 1 | 0.051-0.052 | 21.6 - 22.2 |
| 8 / 2 | 0.045-0.049 | 19.1 - 20.6 |
| 4 / 2 | 0.026-0.028 | **10.9 - 11.7** |

Rule 1 (> $0.05/run -> K 16 -> 12 first): triggered at cpu8/rtf1 (0.09-0.10) and cpu4/rtf1 (0.051-0.052, marginal);
NOT triggered at cpu8/rtf2 (0.045-0.049, marginal) or cpu4/rtf2 (0.026-0.028).

Recommendation:
1. Run the double at **cpu=4, max_rtf=2**: $0.026-0.028 per 720 s run, 6.1 min per mission, boot 3-7 s. This is
   31-35 % under the plan's $0.04 assumption.
2. At that setting the 424-run plan is $10.9-11.7, still above $10.6, so apply steps (2) and (3): tuning 6 configs per
   arm and no-map / timing oracle on day 10 only. Result $8.9-9.5. K stays 16; step (4) is not needed. Rule 1 does not
   fire.
3. If the lead decides the double must run at max_rtf 1 (for example for parity with Isaac), cpu=4 alone gives
   $0.051-0.052 per run; steps (1)-(4) leave $14.2-14.7, still over $10.6, so step (5) applies: ask the user before G2.
   Rule 1 fires there (K 16 -> 12 first).
4. The Modal general table in PLAN_TWIN section 6 (tuning $2.6, dev $1.6, sealed $12.8) at the measured cpu4/rtf2
   cost reads: tuning 64 x 0.0277 = $1.77, dev 40 x 0.0277 = $1.11, sealed 320 x 0.0277 = $8.86 (lifetime basis), a total of

## Limits

- 2 runs per setting; one slow-host outlier (cpu8 rtf1 seed 21, +45 s). Run-to-run noise on a normal host is about 1 s of
  wall at rtf 2, so the cpu4/rtf2 number is stable; the bill is dominated by wall x reservation, not by CPU use.
- Stand-in map (see above). The twin double will differ from the body-shop fake (new plant, new mission length); this
  probe prices the body-shop harness, as H1 specifies. If the twin double ends missions early or loads the CPU
  differently, re-measure with one run at G1.
